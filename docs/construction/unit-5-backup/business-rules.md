# Business Rules — Unit 5: Backup

| ID | Rule (condition → outcome) | Source |
|----|----------------------------|--------|
| BR-1 | `write_backup` with `paths.account` different from `client.account`, or a client with no fingerprint (not from `connect`) → `ValidationError`; nothing is read or written. | FR-ACCT.4 |
| BR-2 | Unless BR-14 applies, `write_backup` calls `discover` (read-only, Unit 4 BR-1, BR-16) and snapshots every live filter in live order: `name` (duplicates numbered, Unit 4 BR-2), `raw_sieve`, `enabled`, plus the `renames`. `live_id` is not stored. | FR-BAK.1, FR-BAK.2 |
| BR-3 | A snapshot is a JSON object with exactly the keys `format` (the integer 1), `created` (UTC, ISO 8601, `Z`), `account`, `fingerprint`, `filters` (list of `name`, `raw_sieve`, `enabled`, in execution order), `renames` (list of `original`, `name`) and `checksum`. The order is the `filters` sequence; there is no separate order field. | FR-BAK.3, FR-ACCT.4 |
| BR-4 | `checksum` is the SHA-256 hex digest of the document without `checksum`, as JSON with sorted keys, compact separators and ASCII escapes. It detects corruption and edits. | FR-BAK.3 |
| BR-5 | The backups directory is created with mode `0o700` if missing. The file `<YYYYMMDDTHHMMSSffffffZ>.json` (UTC) is created exclusively with mode `0o600`; a name that already exists → `BackupError`, and the existing file is never opened for writing. | FR-BAK.3 |
| BR-6 | An I/O failure after the file was created → the partial file is removed and `BackupError` names the path and the reason. If removal fails the error says so (the file fails BR-10 on any read). An I/O failure before creation → `BackupError` naming the path. | FR-BAK.3, FR-BAK.4 |
| BR-7 | A `ClientError` from `discover` propagates; nothing is written. | FR-BAK.2 |
| BR-8 | After a new file is complete, `write_backup` appends one `write` audit line: outcome `backup`, detail `file` (name only), `filters` (count), `renamed` (count); never names or content. If the audit write fails, `SieveAsCodeError` is raised with the cause chained; the valid snapshot stays on disk. | NFR-SAFE.2, NFR-SAFE.3 |
| BR-9 | `read_backup(ref)` resolves `ref`: `None` → the lexicographically greatest `*.json` name in the backups directory (the timestamp sorts chronologically); an existing file → that file; otherwise → that name in the backups directory, `.json` optional. No backup, or no such file → `BackupError`. | FR-BAK.4 |
| BR-10 | Reading verifies, in order: the file is readable; it parses as a JSON object; `format` equals 1 (another value → `BackupError` naming the version found, since a newer format may differ); it has exactly the BR-3 keys; `checksum` matches BR-4; every field has its BR-3 type, and each `name` is non-empty and unique among `filters`; `fingerprint` equals the expected one (BR-13). The first failure → `BackupError` naming the file and the check, never filter content. | FR-BAK.3, FR-ACCT.4 |
| BR-11 | A verified read returns a `Snapshot` whose `state` is a `FilterSet` (`live_id` None, order from `filters`, `renames`) that `diff` accepts in snapshot mode (Unit 4 BR-19). | FR-BAK.5 |
| BR-12 | `diff_backups(a, b)` reads both snapshots (BR-9, BR-10; the expected fingerprint is the one in `paths.account_marker`, a missing or unreadable marker → `BackupError`) and returns `diff(b.state, a.state, None)`: what changed from A to B. `create` entries are filters added in B; `live-only` entries are filters only in A. It calls no Proton command and writes no audit line. | FR-BAK.5 |
| BR-13 | The fingerprint check compares fingerprints only; the recorded account name is informational, so a renamed profile on the same Proton account is accepted. | FR-ACCT.4 |
| BR-14 | After BR-1 and `discover`, `write_backup` reads the latest snapshot (BR-9 with no ref, BR-10 with the client's fingerprint). If it verifies and its `state` equals the live state (names, scripts, `enabled`, order, `renames`; not the timestamp), nothing is written and that `Snapshot` is returned with `unchanged` true. No backup, or a latest that fails BR-10 (including another account's), is not a skip: a new backup is taken. Only the latest is compared. | FR-BAK.2 |
| BR-15 | A skip (BR-14) appends one `check` audit line: outcome `unchanged`, detail `file`, `filters`, `renamed` as in BR-8. An audit failure raises as in BR-8. | FR-BAK.2, NFR-SAFE.3 |
| BR-16 | `prune_backups(paths, keep)` considers only regular files in the backups directory named `<YYYYMMDDTHHMMSSffffffZ>.json` with a valid UTC date; everything else is left alone. Neither `keep.keep_days` nor `keep.keep_last` set, or no directory → nothing is removed. | FR-BAK.6 |
| BR-17 | A candidate is kept if it is one of the newest `keep_last`, or its name's time is within the last `keep_days` days, or it is the newest candidate; the rest are removed. Time comes from the name, not the file's modification time. | FR-BAK.6 |
| BR-18 | If anything was removed, `prune_backups` appends one `write` audit line: outcome `prune`, detail `removed` and `kept` counts. A removal that fails → `BackupError` naming the file after the audit line for those already removed; files removed before it stay removed. It returns the removed names. Only the `backup` command calls it; `write_backup`, `read_backup` and `diff_backups` never delete. | FR-BAK.6, NFR-SAFE.2 |
