# Business Rules — Unit 6: Apply and restore

| ID | Rule (condition → outcome) | Source |
|----|----------------------------|--------|
| BR-1 | `apply_plan` or `restore` with `paths.account` different from `client.account`, or a client with no fingerprint (not from `connect`) → `ValidationError`; nothing is read, written or audited. | FR-ACCT.4 |
| BR-2 | `apply_plan` loads the declared files, then reads live state and targets once (`load_declared`, `discover`, `discover_targets`) and computes `diff(declared, live, targets)` (Unit 4 BR-3–14). That one live read is both the plan and the source of ids for the writes. A `ValidationError` or `ClientError` propagates before any write; `apply_plan` does not call `plan` and appends no plan audit line. | FR-APPLY.1, FR-APPLY.2 |
| BR-3 | A plan with no missing target, entry or reorder → no snapshot, no write, no audit line; the report is `ok` and empty. Flags, informational names and renames alone are not writes. | NFR-REL.1 |
| BR-4 | Writes planned and `confirmed` false → nothing is written and no snapshot is taken; the report carries the plan with `refused` true, and one `check` audit line is appended: outcome `refused`, detail `command`, `actions` (count). | FR-APPLY.1, NFR-SAFE.1 |
| BR-5 | Writes planned and `confirmed` true → before the first write, `write_backup` takes a snapshot (an existing snapshot equal to live state counts, Unit 5 BR-14) and `read_backup` re-reads it for the client's fingerprint. Any failure → the error is raised and nothing is written. The report carries the snapshot. | FR-BAK.1, FR-APPLY.5, FR-BAK.4 |
| BR-6 | The actions, in order, are: each missing target (parents first, as the plan lists them), each plan entry in plan order, then the reorder. One action is one client call: `folder` → `create_folder` (leaf name, parent id from BR-8), `label` → `create_label`, `create` → `create_filter(name, declared script, declared enabled)`, `content` → `update_filter(live_id, declared script)`, `enabled` → `enable_filter` or `disable_filter` per the entry's value, `live-only` → BR-9, `reorder` → `reorder_filters(ids)`. Only filters with an entry are written. | FR-APPLY.2, FR-APPLY.3 |
| BR-7 | The reorder names the declared sequence (the restore: the snapshot's) as ids: the live id for a filter that existed, the id `create_filter` returned for one created in this run. Filters not named (live-only ones) keep their order after them (Unit 4 BR-9). | FR-APPLY.2 |
| BR-8 | A `folder` action resolves its parent when it runs: `list_folders`, the entry whose `path` equals the parent path case-insensitively. A top-level folder has no parent. A parent not found → that action fails (BR-10). | FR-APPLY.2 |
| BR-9 | A `live-only` entry → `disable_filter(live_id)`. With `allow_delete` true (apply) → `delete_filter(live_id)`; the snapshot of BR-5 is that run's verified backup. `restore` always deletes (BR-17). Nothing else is ever deleted. | FR-APPLY.5, RVQ-Q4 |
| BR-10 | The first action whose client call raises `ClientError` ends the run: it is `failed` with the error's message (already first line, capped at 200 characters, NFR-SAFE.2), every later action is `not_attempted`, earlier ones are `succeeded`. No rollback, no retry. | FR-APPLY.4 |
| BR-11 | After each action's outcome, one `write` audit line is appended: outcome `ok` or `failed`, detail `command` (`apply` or `restore`), `action` (kind), `name` (the target or filter name; `order` for the reorder) and, on failure, `exit_code`. Never a script or a reason text. | FR-APPLY.6, NFR-SAFE.2, NFR-SAFE.3 |
| BR-12 | A failing audit write never replaces the report: the action keeps its outcome, the run ends as in BR-10 (the rest `not_attempted`), `audit_error` holds the message, and the report is returned. | FR-APPLY.4, FR-APPLY.6 |
| BR-13 | `ApplyReport.ok` is true when the run was not refused, nothing failed, and `audit_error` is None. `succeeded`, `not_attempted` keep action order. A second `apply_plan` after an `ok` run finds a clean plan (BR-3). | FR-APPLY.4, NFR-REL.1 |
| BR-14 | A flag (Unit 4 BR-12) never blocks or changes a run; it is in the report's plan for the caller to show. | FR-PLAN.5 |
| BR-15 | `restore` first calls `read_backup(ref, paths, client.fingerprint)` (Unit 5 BR-9, BR-10; `ref` None = latest). A `BackupError` propagates before live state is read or anything is written. | FR-BAK.4 |
| BR-16 | The restore plan is `diff(snapshot.state, discover(client), None)` (snapshot mode, Unit 4 BR-19: no target check, no `missing_targets`, no flags), and its writes are that plan's entries and reorder plus every name in `informational`: a disabled filter created after the backup is also deleted, so a restore leaves exactly the backup's filters. The report carries the plan that will run: every such deletion is a `live-only` entry and `informational` is empty. | FR-BAK.4, RVQ-Q21, RVQ-Q33 |
| BR-17 | Restore actions use BR-6 and BR-7 with the snapshot as the desired state, and `live-only` entries and informational names become `delete` actions (in live order, at the live-only position of BR-6). A filter recreated under a numbered name (Unit 5) keeps that name. Audit lines carry command `restore` (BR-11). | FR-BAK.4, FR-APPLY.5 |
| BR-18 | A restore plan with no entry, reorder or informational name → no snapshot, no write, no audit line; the report is `ok` with `remaining` None. | NFR-REL.1 |
| BR-19 | Writes planned and `confirmed` false → refused exactly as BR-4 (command `restore`); the report carries the plan. | FR-BAK.4, NFR-SAFE.1 |
| BR-20 | Writes planned and `confirmed` true → the pre-restore snapshot of the current live state is taken and re-read as in BR-5 before the first write; failure raises and nothing is written. The report carries it so the caller prints its path. | FR-BAK.4 |
| BR-21 | When every action succeeded, `restore` reads live state again (`discover`) and sets `remaining` to `diff(snapshot.state, live, None)`. The report is `ok` only when no action failed, `audit_error` is None, and `remaining` has no entry, no reorder and no informational name. A `ClientError` on that read is `failed` with action kind `verify`, name `live`; `remaining` stays None. | FR-BAK.4, US-3.2 |
| BR-22 | After BR-21, one `check` audit line is appended: outcome `verified` (nothing remaining) or `drift`, detail `entries`, `informational`, `reordered` (0 or 1). An audit failure sets `audit_error` as in BR-12. | FR-BAK.4, NFR-SAFE.3 |
